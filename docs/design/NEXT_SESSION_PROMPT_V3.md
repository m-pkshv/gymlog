`Pixel_8` (`emulator-5554`) уже настроен и использовался всю сессию — если не запущен, поднять: `emulator.exe -avd Pixel_8 -no-snapshot-load`, дождаться `adb wait-for-device shell 'while [[ -z $(getprop sys.boot_completed) ]]; do sleep 1; done'`. Один раз за сессию упал в фоне без видимой причины между шагами — если это повторится, просто перезапустить тем же способом, диск/данные AVD переживают падение.

На нём стоит IronBook (`dev.ironbook.app`) с реальным сидом упражнений, несколькими тестовыми тренировками из прошлых сессий и **52 тестовыми записями веса** (пн/ср/пт, 13 апреля — 10 августа, колебания 80–85 кг с 4 циклами) — добавлены прямой правкой файла БД на устройстве, **не через код/сид приложения**, поэтому их нет ни в репозитории, ни в свежей установке. Пропадут при `-wipe-data`/пересоздании AVD. Язык интерфейса на устройстве переключён на **русский через «Настройки» приложения** (не через системную локаль) — если нужен английский для проверки, переключить там же.

Если понадобится ещё раз что-то похожее (насыпать тестовые данные прямо в БД на эмуляторе, минуя UI) — рабочая техника (подробности и точные команды — раздел «Редизайн интерфейса v3», Шаг без коммита, в `CLAUDE.md`):
- **Вытащить** файл БД: `adb exec-out run-as dev.ironbook.app cat app_flutter/gymlog.sqlite`, поймать как raw byte stream через PowerShell (`[Diagnostics.Process]` + `StandardOutput.BaseStream.CopyTo(MemoryStream)`) — **не** через git-bash `>`-редирект, он портит бинарные данные на Windows (уже проверено в этом и прошлых проектных сессиях).
- Открыть локальную копию тем же кодом приложения (`AppDatabase(NativeDatabase(File(...)))` в одноразовом Dart-скрипте под `flutter test`, удалить после использования) — так гарантированно совпадает схема.
- **Залить обратно**: `adb push <файл> /data/local/tmp/x` (обычный push, `shell` владеет этой директорией), затем `adb shell run-as dev.ironbook.app cp /data/local/tmp/x app_flutter/gymlog.sqlite` (`run-as`-uid не может ни читать, ни писать в `/data/local/tmp` напрямую при попытке ТУДА что-то положить, но спокойно читает то, что туда уже положил `shell`, и пишет в свою же папку).
- Прямая запись из-под `run-as` ни в `/data/local/tmp`, ни во внешнее хранилище `/sdcard/Android/data/<pkg>/` не работает на этом образе Android (`Permission denied` даже на `mkdir`) — не тратить время на повторные попытки.
- Перед закрытием соединения — `PRAGMA wal_checkpoint(TRUNCATE)`, чтобы на диске остался целостный снимок, а не файл в WAL-режиме.

## Технические находки этой сессии по `fl_chart` (пригодятся при следующих правках графиков)

- **`AxisChartData.minIncluded`/`maxIncluded`** (форсируют подпись у точного значения min/max данных) жёстко `true` и **не выведены** в конструктор `LineChartData` — управлять напрямую нельзя. Обход: подобрать `minY`/`maxY` так, чтобы они точно совпадали с обычной сеткой подписей (`lib/core/nice_axis_bounds.dart`).
- **`checkToShowVerticalLine`** по умолчанию получает только координаты, которые `fl_chart` сам посчитал «эффективным интервалом» для оси X — НЕ каждый индекс. Если нужен грид/подписи на произвольном, самостоятельно вычисленном наборе позиций (как для дат-тиков), обязательно ставить `verticalInterval: 1` (и аналогично `interval: 1` для `SideTitles`), иначе колбэк может молча не вызваться на нужных позициях — на регулярных данных совпадение может маскировать баг (как было на месячном виде графика веса), пока не проверишь на нерегулярных (как «Всё время»).
- **`DateFormat.MMM`** (и вообще любой `intl`-форматтер, завязанный на локаль) в голом `flutter test` без дерева виджетов бросает `LocaleDataException` — в реальном приложении инициализация скрыта побочным эффектом `MaterialApp`'s локализационных делегатов. В unit-тесте нужно явно: `import 'package:intl/date_symbol_data_local.dart'; setUpAll(initializeDateFormatting);`.
- **Проверка контраста цвета — считать, не смотреть на глаз.** При подгонке `primary`-цвета под макет посчитал WCAG-контраст явной формулой (относительная яркость + отношение) для `onPrimary`/`onPrimaryContainer` на новых цветах в обеих темах, прежде чем решать, нужно ли их тоже менять — в тёмной теме белый текст на новом `primary` дал бы всего 2.15:1 (провал), а уже существующий тёмный текст — 6.10:1 (порядок). Не полагаться на визуальную оценку «читается/не читается».

## Формат работы (продолжай так же)

- Маленькие шаги: правка → `flutter analyze` + `flutter test` зелёные → коммит **только по явному запросу** («закомить»).
- Push — тоже только по явному запросу («запуш»); проверять `git status`/`git log` перед пушем, чтобы не пушить лишнего и не путать, что уже отправлено.
- Неоднозначность, задевающая данные/схему/новые зависимости — сначала `AskUserQuestion`, потом действие (как было с цветами макета — три вопроса разом одним вызовом, не по одному).
- Косметические мелочи — решай сам, но кратко объясняй решение в отчёте.
- Один коммит на одну логическую правку, не пачками — так было в этой сессии (8 коммитов на 8 разных находок), продолжай в том же духе.
- После реализации — собирай debug-сборку и ставь на уже запущенный `Pixel_8` (`adb install -r`, затем `adb shell am start -n dev.ironbook.app/.MainActivity`) для визуальной проверки перед тем, как отчитываться о готовности; используй `adb shell uiautomator dump` для точных координат элементов вместо оценки по скриншоту на глаз (масштаб скриншота в чате не совпадает с реальным разрешением устройства — координаты для тапов нужно брать из `bounds="[...]"` в дампе, не пересчитывать вручную по картинке).
- Владелец часто присылает скриншот с приложенным текстом-указанием — читай оба вместе, иногда важная деталь (например, что именно должно измениться) есть только в тексте, а скриншот только иллюстрирует «где именно».
