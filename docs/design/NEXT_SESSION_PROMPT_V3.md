На устройстве стоит IronBook (`dev.ironbook.app`) с реальным сидом упражнений, несколькими тестовыми тренировками из прошлых сессий и **52 тестовыми записями веса** (пн/ср/пт, 13 апреля — 10 августа, колебания 80–85 кг с 4 циклами) — добавлены прямой правкой файла БД на устройстве, **не через код/сид приложения**, поэтому их нет ни в репозитории, ни в свежей установке. Пропадут при `-wipe-data`/пересоздании AVD или при `adb uninstall` (уже случалось один раз в этой ветке — после этого их пришлось восстанавливать заново тем же способом ниже). Язык интерфейса на устройстве переключён на **русский через «Настройки» приложения** (не через системную локаль) — если нужен английский для проверки, переключить там же.

Рабочая техника «насыпать тестовые данные прямо в БД на эмуляторе, минуя UI» (использована трижды за три сессии, все три раза успешно — детали и точные команды в `CLAUDE.md`, раздел «Редизайн интерфейса v3», Шаги без коммита и Шаг 11):
- **Вытащить** файл БД: `adb exec-out run-as dev.ironbook.app cat app_flutter/gymlog.sqlite > локальный_путь.sqlite` — на Windows/git-bash обычный `>`-редирект в этот раз сработал нормально (в одной из прошлых сессий раньше требовал PowerShell `MemoryStream`-обходной путь; если снова начнёт портить бинарные данные — вернуться к тому способу).
- Открыть локальную копию тем же кодом приложения (`AppDatabase(NativeDatabase(File(...)))` в одноразовом Dart-скрипте, запускаемом через `flutter test <файл>.dart`, удалить после использования) — так гарантированно совпадает схема (`toInsertCompanion`-мапперы в `lib/data/mappers/` показывают точный тип каждого поля Companion — например, `date`/`createdAt`/`updatedAt` у `BodyMeasurements` это `String`, не `DateTime`; свериться с маппером перед тем, как писать вставку вручную, а не угадывать типы).
- **Залить обратно** — здесь важна тонкость с путями Git Bash на Windows: `adb push` и `adb shell ... /data/local/tmp/...` манглит `/data/local/tmp/...` в `C:/Program Files/Git/data/local/tmp/...`, если МАШИНА уже применила path conversion. Решение — выставить `export MSYS_NO_PATHCONV=1` для всей команды, но тогда конвертировать вручную и ЛОКАЛЬНЫЙ путь тоже (иначе adb не найдёт файл на диске): взять путь вида `/c/Users/...` и вручную заменить префикс на `C:/Users/...` (просто замена строки, не `cygpath`). Тогда: `adb push "C:/Users/.../локальный_путь.sqlite" /data/local/tmp/x` (обычный push, `shell` владеет этой директорией), затем `adb shell run-as dev.ironbook.app cp /data/local/tmp/x app_flutter/gymlog.sqlite` (`run-as`-uid не может ни читать, ни писать в `/data/local/tmp` напрямую при попытке ТУДА что-то положить, но спокойно читает то, что туда уже положил `shell`, и пишет в свою же папку).
- Прямая запись из-под `run-as` ни в `/data/local/tmp`, ни во внешнее хранилище `/sdcard/Android/data/<pkg>/` не работает на этом образе Android (`Permission denied` даже на `mkdir`) — не тратить время на повторные попытки.
- Перед закрытием соединения — `PRAGMA wal_checkpoint(TRUNCATE)`, чтобы на диске остался целостный снимок, а не файл в WAL-режиме.
- После заливки: `adb shell am force-stop dev.ironbook.app`, затем `adb shell monkey -p dev.ironbook.app -c android.intent.category.LAUNCHER 1` — приложение должно быть полностью убито перед перезапуском, иначе продолжит работать со старым состоянием БД в памяти.

## Технические находки этой серии сессий по `fl_chart` (пригодятся при следующих правках графиков)

- **`AxisChartData.minIncluded`/`maxIncluded`** (форсируют подпись у точного значения min/max данных) жёстко `true` и **не выведены** в конструктор `LineChartData` — управлять напрямую нельзя. Обход: подобрать `minY`/`maxY` так, чтобы они точно совпадали с обычной сеткой подписей (`lib/core/nice_axis_bounds.dart`).
- **`checkToShowVerticalLine`** по умолчанию получает только координаты, которые `fl_chart` сам посчитал «эффективным интервалом» для оси X — НЕ каждый индекс. Если нужен грид/подписи на произвольном, самостоятельно вычисленном наборе позиций (как для дат-тиков), обязательно ставить `verticalInterval: 1` (и аналогично `interval: 1` для `SideTitles`), иначе колбэк может молча не вызваться на нужных позициях — на регулярных данных совпадение может маскировать баг (как было на месячном виде графика веса), пока не проверишь на нерегулярных (как «Всё время»).
- **`preventCurveOverShooting`/`preventCurveOvershootingThreshold`** не помогают против «горбов» на почти-плоских участках линии, даже на большом пороге (проверено: 10 и 60 рендерятся идентично) — внутри `fl_chart` эта проверка сравнивает *знаковую* (не абсолютную) разницу пикселей соседних точек с положительным порогом, поэтому гасит выпуклость почти только на подъёме, никогда — на плато. Единственный реально работающий рычаг против таких горбов — снижение `curveSmoothness` (сейчас `0.15` в обоих графиках приложения).
- **`FlDotData()` дефолт** — `FlDotCirclePainter(radius: 4)`; при `barWidth: 3` это заметно толще линии («шарик»). Если нужно тоньше — явный `getDotPainter: (spot, percent, barData, index) => FlDotCirclePainter(radius: X, color: ...)`.
- **`DateFormat.MMM`** (и вообще любой `intl`-форматтер, завязанный на локаль) в голом `flutter test` без дерева виджетов бросает `LocaleDataException` — в реальном приложении инициализация скрыта побочным эффектом `MaterialApp`'s локализационных делегатов. В unit-тесте нужно явно: `import 'package:intl/date_symbol_data_local.dart'; setUpAll(initializeDateFormatting);`.
- **Проверка контраста цвета — считать, не смотреть на глаз.** При подгонке `primary`-цвета под макет посчитал WCAG-контраст явной формулой (относительная яркость + отношение) для `onPrimary`/`onPrimaryContainer` на новых цветах в обеих темах, прежде чем решать, нужно ли их тоже менять — в тёмной теме белый текст на новом `primary` дал бы всего 2.15:1 (провал), а уже существующий тёмный текст — 6.10:1 (порядок). Не полагаться на визуальную оценку «читается/не читается».

## Быстрая визуальная диагностика без цикла APK build+install+screenshot

Для перебора визуальных параметров (кривизна линии, размер точек, отступы и т.п.) не обязательно каждый раз пересобирать и переустанавливать APK — можно отрендерить конкретный виджет в PNG прямо внутри `flutter test`, это на порядок быстрее (секунды против минут):

```dart
// test/_scratch_chart_diag_test.dart — временный файл, удалить после использования
testWidgets('diagnostic render', (tester) async {
  tester.view.physicalSize = const Size(900, 900);
  tester.view.devicePixelRatio = 1.0;
  addTearDown(tester.view.resetPhysicalSize);
  addTearDown(tester.view.resetDevicePixelRatio);

  await tester.pumpWidget(MaterialApp(home: Scaffold(body:
    RepaintBoundary(key: const Key('boundary'), child: /* виджет под тестом */),
  )));
  await tester.pump();
  await tester.pump(const Duration(milliseconds: 500));

  final boundary = tester.renderObject<RenderRepaintBoundary>(find.byKey(const Key('boundary')));
  await tester.runAsync(() async {
    final image = await boundary.toImage(pixelRatio: 2.0);
    final bytes = await image.toByteData(format: ui.ImageByteFormat.png);
    await File(r'путь_в_scratchpad\diag.png').writeAsBytes(bytes!.buffer.asUint8List());
  });
});
```

Критично: весь блок `toImage`/`toByteData`/`writeAsBytes` обязательно оборачивать в `tester.runAsync(() async { ... })` — голый `dart:io` I/O внутри `testWidgets` без этого зависает на 10 минут (таймаут теста) без единого исключения в выводе (уже дважды пойманная в проекте находка — впервые на Этапе 11/Шаг 1 для `UserProfileService`, повторно на этой же серии сессий для графиков). Готовое изображение читать через `Read`-инструмент — так можно оценивать результат визуально прямо в диалоге, без выхода на устройство. Финальную проверку перед коммитом всё равно стоит делать на реальном (эмуляторном) рендере `fl_chart`/системных шрифтов — эта техника для быстрой ПРЕДварительной итерации, не замена on-device проверки.

Один раз за все сессии APK-сборка на эмуляторе визуально не отражала уже применённые изменения кода, хотя `flutter clean`+пересборка помогли — точная причина не установлена (возможно, артефакт Gradle-кэша), диагностика прекращена в пользу более быстрого test-based пути выше. Если увидишь то же самое — не трать время на разбор причины, просто `flutter clean` + пересборка + переустановка (учти: это стирает данные приложения, если делать `adb uninstall`, а не просто пересобрать APK и поставить `adb install -r`).

## Формат работы (продолжай так же)

- Маленькие шаги: правка → `flutter analyze` + `flutter test` зелёные → визуальная проверка (test-render для быстрой итерации, затем реальная APK-сборка на эмуляторе перед финальным отчётом) → коммит **только по явному запросу** («закомить»).
- Push — тоже только по явному запросу («запуш»); проверять `git status`/`git log` перед пушем, чтобы не пушить лишнего и не путать, что уже отправлено.
- После явного запроса «закомить»/«запуш» — не забыть обновить `CLAUDE.md` (запись по установившемуся формату «Шаг N») отдельным `docs:`-коммитом, как это делалось на каждом шаге этой серии (два коммита на шаг: код+тесты, затем документация) — не смешивать код и документацию в одном коммите, это устоявшийся в проекте паттерн для этой ветки.
- Неоднозначность, задевающая данные/схему/новые зависимости — сначала `AskUserQuestion`, потом действие (как было с цветами макета — три вопроса разом одним вызовом, не по одному).
- Косметические мелочи — решай сам, но кратко объясняй решение в отчёте.
- Один коммит на одну логическую правку, не пачками — так было во всех сессиях (по коммиту на находку, иногда с несколькими под-итерациями внутри одного коммита, если находка потребовала нескольких раундов правок по живой пробе, как Шаг 10 или Шаг 11 этой ветки).
- После реализации — собирай debug-сборку и ставь на уже запущенный `Pixel_8` (`adb install -r`, затем `adb shell am force-stop dev.ironbook.app && adb shell monkey -p dev.ironbook.app -c android.intent.category.LAUNCHER 1`) для визуальной проверки перед тем, как отчитываться о готовности; используй `adb shell uiautomator dump` для точных координат элементов вместо оценки по скриншоту на глаз (масштаб скриншота в чате не совпадает с реальным разрешением устройства — координаты для тапов нужно брать из `bounds="[...]"` в дампе, не пересчитывать вручную по картинке; для Flutter-виджетов UIAutomator текстового содержимого не видит вообще — навигация только по вычисленным координатам, сверенным со скриншотом).
- Владелец часто присылает скриншот с приложенным текстом-указанием — читай оба вместе, иногда важная деталь (например, что именно должно измениться) есть только в тексте, а скриншот только иллюстрирует «где именно».
- Финальный скриншот с эмулятора стоит присылать владельцу через `SendUserFile`, а не просто описывать словами — в этой серии сессий это несколько раз ловило расхождение между тем, что задумано, и тем, что реально получилось на экране.
