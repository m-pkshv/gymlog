## Диагностика этой сессии (полная хронология, чтобы не повторять уже пройденные тупики)

1. **Проверено и подтверждено рабочим, НЕ являлось причиной**: `POST_NOTIFICATIONS` разрешение выдано; канал уведомлений `rest_timer` создан с `importance=HIGH`; все переключатели показа уведомлений в MIUI включены на максимум; `AlarmManager`-будильник срабатывал точно по расписанию каждый раз (подтверждено через `adb shell dumpsys alarm` + `logcat` — процесс приложения просыпался специально под будильник, крашей в логе нет).
2. **MIUI Автозапуск был выключен** — частая на Xiaomi причина фонового ограничения. Владелец включил — **не помогло**.
3. **Первая найденная реальная причина — иконка уведомления**: `NotificationService.initialize()` использовал `@mipmap/ic_launcher` (adaptive-иконка, слои фона/переднего плана с Этапа 12/Шаг 2) как маленькую иконку в шторке — Android/MIUI не может использовать adaptive-иконку в этой роли и тихо отбрасывает такое уведомление без ошибки в логе. Создан `android/app/src/main/res/drawable/ic_notification.xml` (монохромный силуэт песочных часов, только прямые линии) — переключено на `'ic_notification'`. **Само по себе не помогло** — уведомление всё ещё не приходило, но это реальный отдельный баг, оставлен исправленным.
4. **Изоляция через диагностические кнопки**: добавлены в «Ещё → Настройки → Уведомления» две постоянные (не временные — решено оставить) кнопки: «Отправить тестовое уведомление» (немедленный `.show()`, без будильника) и «Запланировать через 10 секунд» (тот же `zonedSchedule`-путь, что у настоящего таймера отдыха). Немедленное — сработало сразу. Отложенное (со старым `AndroidScheduleMode.inexactAllowWhileIdle`) — не сработало, точно как настоящий таймер. Это изолировало проблему именно на пути «доставка из фонового будильника», а не в конкретно rest-timer коде.
5. **Переход на `AndroidScheduleMode.alarmClock`** (владелец подтвердил через `AskUserQuestion`) — самый надёжный режим на Android, освобождён от Doze/энергосбережения. Сразу дал новую, более специфичную ошибку: `PlatformException(exact_alarms_not_permitted)`. Поймана временным выводом сырого текста исключения в snackbar диагностической кнопки (в release-сборке `run-as` недоступен без root, файл `app.log` иначе не прочитать) — потом убран обратно на обычное сообщение, причина уже найдена.
6. **Настоящая причина**: на Android 14+/HyperOS режим `alarmClock` требует отдельного специального разрешения «Будильники и напоминания» (`SCHEDULE_EXACT_ALARM`) — это НЕ runtime-диалог (как у камеры/уведомлений), а тумблер в системных настройках, который пользователь включает вручную один раз. Добавлено (владелец подтвердил): `<uses-permission android:name="android.permission.SCHEDULE_EXACT_ALARM"/>` в манифест; `NotificationService.hasExactAlarmPermission()`/`requestExactAlarmPermission()` через `permission_handler`'s `Permission.scheduleExactAlarm` (открывает системный экран напрямую); новый контекстный диалог `_ensureExactAlarmPermissionRequested()` в `lib/features/workout_editor/screen.dart` — показывается один раз, сразу после уже существующего диалога про обычные уведомления (тот же паттерн «спросить один раз через SharedPreferences-флаг»).

**Собрана и установлена сборка с этим фиксом, но владелец ещё не подтвердил результат.**

## Как проверить руками (первое действие следующей сессии, если ещё не сделано)

1. Установить актуальную сборку (переустановка поверх существующей БД безопасна, схема не менялась в этой сессии).
2. Открыть/создать тренировку → добавить подход → отметить ✓.
3. Должен появиться (если ещё не был подтверждён раньше) диалог «Включить уведомления?», затем новый диалог «Разрешить точные напоминания?» → нажать «Открыть настройки».
4. В открывшемся системном экране включить тумблер «Будильники и напоминания» для IronBook вручную.
5. Вернуться в приложение, повторить проверку — либо новым подходом ✓, либо (быстрее) кнопкой «Запланировать через 10 секунд» в «Ещё → Настройки → Уведомления».
6. Уведомление должно появиться даже с заблокированным экраном.

Если не появилось — проверить `adb shell dumpsys alarm | grep -A5 ironbook` (будильник вообще поставлен?) и `adb logcat -d -v time | grep -i notif` сразу после срабатывания.

## Технические находки этой сессии (уроки, актуальны и дальше)

- **XML-комментарии: двойной дефис `--` внутри тела комментария запрещён спецификацией** и валит Gradle-сборку (`ManifestMerger2$MergeFailureException`/`ParseLibraryResourcesTask`) без явной подсказки на первый взгляд. Наступил на это дважды в этой сессии (`ic_notification.xml`, затем `AndroidManifest.xml`) — уже было задокументировано раньше в истории проекта, но фактически забылось. **Проверять каждый новый/изменённый XML-комментарий на `--` перед сборкой.**
- **`AndroidScheduleMode.inexactAllowWhileIdle` может надёжно будить процесс по расписанию, но не гарантирует доставку самого уведомления** на некоторых OEM-прошивках (подтверждено на MIUI/HyperOS) — будильник срабатывает, `zonedSchedule`-колбэк исполняется, но `.show()` из этого фонового контекста может тихо не долетать до шторки. `alarmClock` надёжнее, но требует `SCHEDULE_EXACT_ALARM` + ручного разрешения на Android 14+.
- **Adaptive-иконка (`@mipmap/ic_launcher` с фон+передний план) нельзя использовать как `smallIcon` уведомления** — нужна отдельная плоская монохромная `drawable/*.xml`.
- **В release-сборке нет доступа к `app.log` через `adb run-as` без root** (не debuggable) — для быстрой диагностики исключения можно временно вывести `error.toString()` прямо в UI (snackbar), убрав диагностику сразу после того, как причина найдена — не оставлять в постоянном коде.
- **`adb shell input tap`/`keyevent` на устройстве владельца бросает `SecurityException: Injecting input events requires... INJECT_EVENTS permission`** — известное, неразрешимое программно ограничение этого конкретного устройства. Взаимодействие с UI на реальном тапе — только руками владельца, подтверждение — через `adb shell screencap`/`pull` после его действия.
- **Mocktail + `captureAny(named: 'delay')` для `Duration`-параметров требует `registerFallbackValue(Duration.zero)` в `setUpAll`** — иначе падает при первом использовании нестандартного (не примитивного) типа с именованным матчером.
