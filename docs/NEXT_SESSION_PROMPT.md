## Новый локальный ресурс: эмулятор для скриншотов

Создан AVD **`IronBook_Screenshots`** (в `C:\Users\Mak\.android\avd\IronBook_Screenshots.avd`) — клон `Pixel_8`, но с принудительно выставленным разрешением экрана **ровно 1080×1920** (точное 9:16 — это жёсткое требование формы скриншотов Play Console). Пригодится, если понадобится переснять/досоздать скриншоты.

Если понадобится создать что-то подобное снова — **`avdmanager create avd` сломан** для установленного системного образа (`system-images;android-37.1;google_apis_playstore_ps16k;x86_64`, ошибка `Could not load devices from ...devices.xml` — файла физически нет нигде в SDK, воспроизведено с разными `-d`-профилями, значит баг образа/инструмента). Рабочий обход: скопировать папку уже существующего рабочего `.avd` под новым именем, вручную поправить `config.ini` (`hw.lcd.width`/`height`/`density`, `skin.name` — можно `WIDTHxHEIGHT` без реального skin-файла), создать/поправить парный `<имя>.ini` в `.android/avd/`, запустить с `-wipe-data` если диски скопированы с ЖИВОГО (работающего) эмулятора.

Запуск: `emulator.exe -avd IronBook_Screenshots -no-snapshot-load`. После установки приложения через `adb install` иконка **не появляется на главном экране лаунчера автоматически** — открывать через `adb shell am start -n dev.ironbook.app/.MainActivity`, не искать иконку вручную.

Реальные скриншоты, снятые владельцем 8 августа, сохранялись на `Desktop\Screenshot_*.png` (эмулятор Android Studio сохраняет туда по умолчанию) — если их там больше нет, переснять тем же способом на этом же эмуляторе.

## Технические находки этой и предыдущих сессий (уроки, актуальны и дальше)

- **При любом вопросе про политику/правила Google Play или Apple — сверяться через `WebSearch`/`WebFetch` по `support.google.com`/`developer.apple.com`, не отвечать по памяти.** Эти политики меняются, а цена неверного ответа высокая (может сорвать публикацию/заблокировать аккаунт). В прошлой сессии это делалось систематически — оба инструмента уже загружены один раз через `ToolSearch`, при необходимости просто вызывай напрямую.
- **`avdmanager create avd` может быть сломан для конкретных системных образов** (см. раздел выше про новый эмулятор) — обход через клонирование существующего рабочего `.avd`, не через попытки чинить `avdmanager`.
- **Google Play Console: обычный email-список тестировщиков и Google Groups — два разных, несовместимых механизма.** Нельзя вписать адрес группы в текстовое поле email-списка, ожидая, что он развернётся в участников — нужно использовать отдельную опцию «Google Groups» в интерфейсе.
- **Смена механизма управления тестировщиками (email-список ↔ Google Groups) для уже частично отработавших тестировщиков — недокументированный риск.** Не переключать, если у кого-то уже идёт отсчёт 14 дней; можно только ДОБАВИТЬ второй механизм, не заменяя первый.
- **`ColorScheme.fromSeed()` — не бесплатная операция.** Если что-то (провайдер, виджет) слушает целиком объект без переопределённого `==`, любое несвязанное изменение поля вызовет полный пересчёт зависимых значений.
- **`flutter_lints` НЕ включает `prefer_const_constructors`/`prefer_const_literals_to_create_immutables`/`prefer_const_declarations` по умолчанию** — теперь включены в `analysis_options.yaml` явно, постоянный страж.
- **`flutter build appbundle --strip` — не существующий флаг.** AGP и так стрипает нативные библиотеки на своём этапе сборки — предупреждение про DWARF относится к промежуточному состоянию, не к финальному `.aab`. Проверять реальный результат напрямую (`llvm-readelf -S`), не доверять тексту предупреждений на слово.
- **Современный `keytool` создаёт keystore в формате PKCS12 по умолчанию** — не поддерживает разные пароли для хранилища и ключа, JDK молча использует один и тот же пароль для обоих.
- **MIUI иногда требует физического подтверждения на экране телефона** при `adb install` — если падает с `INSTALL_FAILED_USER_RESTRICTED`, проверить экран устройства, а не считать это стабильной ошибкой adb.
- **Android не даёт установить пакет с другой подписью поверх уже установленного** (`INSTALL_FAILED_UPDATE_INCOMPATIBLE`) — переход debug↔release требует удаления старого приложения (теряются локальные данные) — спрашивать явное подтверждение перед этим.
- **XML-комментарии: двойной дефис `--` внутри тела комментария невалиден** и валит сборку — проверять новые/изменённые XML-комментарии на `--` до сборки.
- **Любой Android-ресурс, к которому обращаются по имени-строке** (`Resources.getIdentifier`), невидим для resource shrinker'а release-сборок и рискует быть тихо вырезан — сразу добавлять `tools:keep` (`android/app/src/main/res/raw/keep.xml`).

## Формат работы (продолжай так же)

- Маленькие шаги: правка → `flutter analyze` + `flutter test` зелёные → коммит **только по явному запросу**.
- Неоднозначность, задевающая данные/схему/новые зависимости/подпись релиза/деньги/аккаунты — сначала `AskUserQuestion`, потом действие.
- Косметические мелочи — решай сам, но кратко объясняй решение.
- Разрушительные действия (удаление приложения с устройства и его локальных данных, git push/merge, что угодно необратимое) — только по явному подтверждению, не молча.
- После реализации — собери сборку, которую попросит владелец (debug по умолчанию, release/appbundle — по явному запросу), и либо отправь через `SendUserFile`, либо установи напрямую при явной просьбе «установи»: `adb install -r -d ...`.
