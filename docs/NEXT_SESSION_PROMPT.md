## Прежде чем писать код — Этап 11 не готов к реализации, только к обсуждению

`docs/02_DEVELOPMENT_PLAN.md`, раздел «Этап 11», сам явно помечен: идеи зафиксированы владельцем «пока не забыл», цель/зависимости/критерии приёмки НЕ уточнены и требуют отдельного разговора перед стартом. Три пункта функциональности и открытые вопросы к каждому (дословно из плана):

1. **Экспорт одной тренировки в PDF** (например, отправить тренеру) — не решено: макет/состав документа (что печатать — план, факт, тоннаж, комментарии, рекорды); библиотека для генерации PDF — это **новая зависимость**, не в TS 3, требует согласования владельца (регламент, раздел 10: запрет добавлять зависимости без согласования).
2. **Профиль пользователя** (ник/имя/фамилия/аватар) — не решено: где хранится (новая таблица БД — реальное изменение схемы, критическая тема регламента, раздел 6); откуда берётся аватar (выбор из галереи — вероятно ещё одна новая зависимость типа `image_picker`) и как/где физически хранится файл.
3. **Экспорт/восстановление резервной копии** — не решено: как это соотносится с уже готовым CSV-экспортом (TS 10, Этап 8) и с системным бэкапом БД (решение TS-1, Этап 10, уже включён) — третий отдельный механизм или переиспользование одного из существующих; формат файла, нужно ли шифрование/пароль (вес/замеры — потенциально чувствительные данные); как подтверждать пользователю необратимость полной перезаписи текущей БД при восстановлении.

Это ровно та ситуация, когда регламент требует: «Сначала критические вопросы, потом код» (`05_AI_INSTRUCTIONS.md`, правило 5) — все три пункта задевают блокирующие темы (схема данных, новые зависимости). **Начни сессию с этих вопросов владельцу через `AskUserQuestion`**, а не с кода. Скорее всего есть смысл разбить на подэтапы и решать по одному пункту функциональности за раз (профиль → бэкап → PDF, или в другом порядке — уточни).

## Уроки прошлых сессий, всё ещё актуальные

- **Не коммить/не пуш без явного запроса в каждом конкретном случае.**
- **Debug-сборка — не показатель реальной производительности** (разы, не проценты). Любая жалоба на скорость — сначала спроси/проверь, на какой сборке тестировал владелец; для честного замера — `flutter build apk --release` (или `--profile`), не `flutter run`.
- **При добавлении временной диагностики (Stopwatch/print для одноразового замера) — обязательно убрать перед коммитом.** `print()` вне логгера запрещён регламентом даже временно оставленным.
- **При реверсе ранее удалённой функциональности — `git log`/`git show` на коммите удаления**, восстанавливать дословно, не изобретать заново.
- ARB-ключи — плоское пространство имён, перед добавлением нового ключа `grep` по обоим `.arb`-файлам на коллизию.
- **`GestureDetector(onTap: ...)` не ловит тапы, если под ним есть кнопка/чекбокс со своим `InkWell`** — тот выигрывает гонку жестов. Нужен `Listener(behavior: HitTestBehavior.translucent, onPointerDown: ...)`.
- **`FocusScope.of(context).unfocus()` не гарантирует сброс** — scope восстанавливает последнее сфокусированное поле. Нужен `FocusManager.instance.primaryFocus?.unfocus()`.
- **В виджет-тестах `Center`/подобные layout-виджеты растягивают свой render-box на весь доступный размер**, а не на размер видимого центрированного потомка — `tester.getTopLeft/getCenter` на finder, ищущий такой widget, даст координаты ВНЕШНЕЙ области, не визуального содержимого. Если нужно кликнуть/анкориться на реально видимый элемент — ищи сам этот элемент (например, конкретные дочерние виджеты), не обёртку.
- Устройство иногда даёт `INSTALL_FAILED_USER_RESTRICTED`/теряет видимость в `adb devices` — обычно решается повторной попыткой; `adb install -r -d ...` (флаг `-d` разрешает даунгрейд версии без потери данных).
- Путь к adb на этой машине: `/c/Users/Mak/AppData/Local/Android/Sdk/platform-tools/adb.exe` (bash) — `export ANDROID_ADB=...` и вызывать через `"$ANDROID_ADB"`.

## Формат работы (продолжай так же)
- Маленькие шаги: правка → `flutter analyze` + `flutter test` зелёные → коммит **только по явному запросу**.
- Неоднозначность, задевающая данные/схему/новые зависимости — сначала `AskUserQuestion`, потом код (особенно важно для Этапа 11, см. выше).
- Косметические мелочи — решай сам, но кратко объясняй решение.
- После реализации — собери debug APK и предложи владельцу проверить на реальном устройстве, прежде чем коммитить.
- Технический писатель в конце этапа/крупного куска работы — обнови `CLAUDE.md` (история шагов + сверка при закрытии) и, если меняется объём/критерии, `docs/02_DEVELOPMENT_PLAN.md`.
